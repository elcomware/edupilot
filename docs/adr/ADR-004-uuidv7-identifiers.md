# ADR-004 — UUIDv7 identifiers

- **Status:** Accepted
- **Date:** 2026-09-29

## Context

EduPilot nodes will create records independently — School A, School B, an offline Node C, and the cloud — and later converge. Auto-increment integers assume a single central allocator and leak volume information.

## Decision

Every entity uses a **UUIDv7** primary key: time-ordered, globally unique, and safe to generate on any node without coordination.

Auto-increment may be used internally for indexing performance but is **never** a business identifier and never appears in documents or APIs.

Business-visible numbers (`REC/LOME/2026/004521`) are separate, generated by the numbering engine.

## Consequences

- Offline creation and later synchronisation work without ID collision or coordination.
- IDs are opaque and do not leak enrolment or transaction volume.
- Index locality is preserved because UUIDv7 is time-ordered.
- 16-byte keys are larger; storage and index size are an accepted trade-off.

## Alternatives considered

- **Auto-increment integers** — rejected: requires a central sequence, breaks offline creation, and leaks counts.
- **ULID** — rejected: equivalent properties but a less widely adopted standard across languages and databases.
- **Snowflake** — rejected: encodes a machine ID, which is meaningless for per-school nodes and complicates multi-tenancy.
